## Constat racine (leçon de l'audit — STRUCTURANT)

`user_has_copro_access(copro)` (0023 l.109-121) renvoie **TRUE pour TOUT membership de la copro**, gestionnaire OU copropriétaire (le filtre cabinet ne borne que le rôle gestionnaire). Conséquence : l'utiliser en SELECT sur une table **back-office** expose ses données au copropriétaire.

**Règle de patron RLS (à appliquer partout) :**
- **Donnée COLLECTIVE** (visible de tout copropriétaire) → SELECT `user_has_copro_access(copro_id)`.
- **Donnée BACK-OFFICE / sensible** (gestionnaire only) → SELECT `user_is_copro_manager(copro_id)`, + éventuel volet « own » lot-centric pour le copropriétaire.
- Toute écriture → `user_is_copro_manager(copro_id)` (sauf exceptions documentées).
- `anon` : aucune policy → aucun accès. `service_role` : bypass RLS (pas de policy).
- Toujours via helper, **jamais** de `copro_id IN (...)` brut (cloisonnement cabinet centralisé).

## Décisions USER (2026-06-07)

1. **platform_admin** : NON seedé en SQL. Seed + gates en `service_role`. Compte réel créé hors migration. → commentaire only.
2. **Indivision** : `coproprietaires` reçoit une 3e policy SELECT bornée aux co-indivisaires des lots détenus (`get_user_lot_ids`).
3. **Votes AG** : écriture par RPC canonique uniquement. PAS de own-write sur `ag_votes`, `ag_attendance` (étendu à `council_votes`, `council_decisions`).
4. **events** : lecture copro (`user_has_copro_access`) + écriture gestionnaire (`user_is_copro_manager`).

Tranché en expert (modifiable) : `profiles` UPDATE-soi fige `cabinet_id` (anti-élévation) ; `email_templates` hybride (système `copro_id NULL` + par-copro) ; COPRO-TEMPLATE = `set_opening_balance` en tête + 2 gates ; seed `work_domain` = assertion (déjà en 0004) ; codes relance `payment_reminder_7/30/60` (alignés sur `create_default_reminder_rules` 0028).
