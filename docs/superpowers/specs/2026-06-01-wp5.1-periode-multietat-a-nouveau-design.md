# WP5.1 — Période comptable multi-état + report à-nouveau — Design

> Date : 2026-06-01 · Projet : CoProFlex · Base : Supabase/Postgres `iyfesbjnkpynmwlsmxnp`
> Cadre légal : décret n° 2005-240 (comptabilité du syndicat), comptabilité d'engagement / droits constatés.
> Lié : [[payment_imputation_rules]] (règle C : encaissement → période ouverte), WP5.2 (cut-off 408/486), WP5.3 (régularisation / affectation).

## 1. Objectif

Permettre de **clôturer un exercice et en ouvrir le suivant proprement**, en **reportant les soldes** (à-nouveau), sans perte ni double comptage. C'est le prérequis du cut-off (WP5.2), de la régularisation (WP5.3) et de la règle d'imputation des paiements à la période ouverte.

## 2. État des lieux (existant en base)

- `accounting_periods` : statut (enum `period_status` = `open|locked|closed|approved|rejected`), `start_date`, `end_date`, `locked_at/by`, `closed_at/by`, `approved_at/by`, `approval_notes`.
- Fonctions présentes : `close_period`, `lock_period`, `get_period_for_date`, `check_single_open_period`.
- Trigger `enforce_single_open_period` (via `check_single_open_period`) : refuse > 1 exercice `open` par copro.
- Comptes de report copro : `110` (solde en attente travaux & opérations exceptionnelles), `120` (solde en attente opérations courantes / report à nouveau).
- **Manque** : aucune fonction d'à-nouveau (report des soldes). C'est le vrai trou.
- **Anomalie** : **4 comptes en doublon sur le code `120`** → à dédoublonner (prérequis).

## 3. Décisions de conception (validées)

1. **Déclenchement en deux étapes** : le gestionnaire clôture N et **ouvre N+1 avec un à-nouveau PROVISOIRE** dès le 1ᵉʳ jour de N+1 ; l'**approbation des comptes en AG** rend l'à-nouveau **DÉFINITIF** (figé).
2. **Mécanisme = écriture de reprise des soldes** : une vraie écriture postée au grand livre de N+1 (pas de soldes cumulés calculés). Le grand livre par exercice reste auto-suffisant (cohérent avec le filtrage `period_id`, cf. #9).
3. **Reprise régénérable (idempotente)** : une RPC (re)génère la reprise depuis les soldes de clôture de N ; rejouable (cut-off tardif dans N → on relance) ; **figée à l'approbation AG**.
4. **Périmètre borné** : WP5.1 s'arrête à **figer l'à-nouveau**. La **répartition excédent/déficit par lot** (120/110 → 450) relève du **WP5.3** ; WP5.1 expose seulement le point d'accroche.
5. **Invariant `enforce_single_open_period` CONSERVÉ** : un seul exercice `open` à la fois = bonne pratique. Pas besoin de deux exercices ouverts ; N reste `locked` pendant que N+1 est `open`.
6. **Immutabilité — exemption ciblée (Option A)** : l'écriture de reprise (`source_type='opening_balance'`) échappe à l'immutabilité du grand livre **tant que l'exercice source N n'est pas `approved`** (régénération en place) ; dès `approved`, l'immutabilité reprend (figée). Une seule entorse, étroite et conceptuellement justifiée (une ouverture provisoire n'est pas un fait définitif).

## 4. Sémantique des états

| Statut | Sens | Écritures autorisées |
|--------|------|----------------------|
| `open` | exercice courant de saisie | opérations courantes (appels, paiements, factures, dépenses) |
| `locked` | gelé pour le courant, en cours de clôture | écritures de clôture/cut-off (WP5.2) + reprise ; **pas** d'opérations courantes |
| `closed` | comptes arrêtés, présentés à l'AG | aucune |
| `approved` | comptes approuvés en AG | aucune ; **fige** la reprise de N+1 ; déclenche le hook WP5.3 |
| `rejected` | comptes rejetés en AG | retour possible en `locked` pour correction |

Transition de bascule : N `open → locked` (libère l'unicité `open`), puis N+1 créé/ouvert. N reste `locked` jusqu'à `closed`/`approved`.

## 5. Contenu de la reprise à-nouveau

Calcul depuis les **soldes de clôture postés de N** (`ledger_entries` joints à `ledger_transactions status='posted'`, `period_id = N`), agrégés par `(account_id, lot_id)`. Une seule écriture équilibrée datée du `start_date` de N+1, `source_type='opening_balance'`, `source_id = id(N)` :

- **Comptes de bilan — reportés à l'identique** (solde de clôture = solde d'ouverture) :
  - Classe 1 : `105` fonds travaux, `103` avances, réserves, etc.
  - Classe 4 : **`450` par lot — conserver `lot_id` ET la nature (`450-1..5`)** ; `401` fournisseurs.
  - Classe 5 : `512` banque, comptes d'attente `47x`.
- **Comptes de gestion (classes 6 et 7) — NON reportés** : leur solde net (produits − charges) = **résultat de l'exercice**, viré en **`120`** (opérations courantes) et **`110`** (travaux & exceptionnel), « en attente d'affectation » jusqu'à l'AG.
- **Équilibre garanti** : la reprise est la balance de clôture reprise → Σ débits = Σ crédits par construction. Postée via `create_ledger_transaction(..., auto_post=true)` ; le garde-fou CR3 (déséquilibre → exception) protège.

## 6. Fonctions & déclencheurs

- **`open_next_period(p_copro_id uuid, p_closing_period_id uuid, p_new_name text DEFAULT NULL, p_new_start date DEFAULT NULL, p_new_end date DEFAULT NULL) RETURNS jsonb`**
  1. Vérifie que N (`p_closing_period_id`) n'est pas `open` (≥ `locked`).
  2. Crée N+1 s'il n'existe pas (dates par défaut = année suivante), sinon le récupère ; le passe `open` (invariant respecté car N n'est plus `open`).
  3. **(Ré)génère** la reprise dans N+1 : si une reprise `opening_balance(source_id=N)` existe et que N n'est pas `approved`, on la **remplace** (suppression permise par l'exemption d'immutabilité) ; recalcul depuis les soldes de clôture de N ; post.
  4. Idempotente : rejouable après un cut-off tardif dans N.
- **Hook d'approbation** (branché sur l'orchestrateur AG existant `finalize_and_activate_ag` / `activate_ag_decisions`, ou une RPC `approve_period`) : passe N `approved`, **fige** la reprise de N+1 (l'exemption ne s'applique plus), puis **appelle le point d'accroche WP5.3** (`regularize_period(...)` — stub no-op pour l'instant, signature définie).
- Fiabiliser `close_period`/`lock_period` (statuts, garde-fous, horodatage).

## 7. Garde-fous & invariants

- `enforce_single_open_period` : **conservé**.
- Immutabilité du grand livre : **exemption ciblée** `source_type='opening_balance'` tant que N ≠ `approved` (cf. décision 6). À implémenter dans le trigger d'immutabilité existant.
- Trigger `trg_enforce_lot_id_on_45x` : la reprise des `450` conserve `lot_id` → conforme.
- Unicité : au plus **une** reprise active par exercice (`source_type='opening_balance'`, `source_id` unique par copro/période cible).
- Posting en `locked` : autoriser les écritures de clôture/reprise (détaillé en WP5.2) ; pour WP5.1, la reprise se poste dans N+1 (`open`).

## 8. Nettoyage 110/120 (prérequis, dans WP5.1)

Migration de dédoublonnage : garder **un seul** compte `120` (et vérifier `110`) par copro, ré-aiguiller toute écriture existante vers le compte conservé, supprimer les doublons. Sans ça, l'à-nouveau ne sait pas sur quel compte virer le résultat.

## 9. Hors périmètre WP5.1

- Les écritures de **cut-off 408/486** elles-mêmes (WP5.2).
- La **répartition excédent/déficit par lot** (120/110 → 450 par quote-part) à l'approbation (WP5.3 ; WP5.1 ne fait qu'exposer le hook).
- Couche **engagement** (WP5.4).

## 10. Tests (sur la boucle d'or — Le Clos `22222222`)

1. Ouvrir **2027** depuis 2026 via `open_next_period` → reprise **équilibrée** (Σ débit = Σ crédit), grand livre 2027 global = 0.
2. **`450` par lot** et **`512`** correctement reportés (solde d'ouverture 2027 = solde de clôture 2026).
3. Solde net 6/7 de 2026 viré en **120/110** (montant = résultat de l'exercice).
4. Vues de 2027 (dashboard trésorerie, solde copropriétaire) affichent les bons soldes d'ouverture.
5. **Rejeu idempotent** : poster une écriture dans 2026 (`locked`), relancer `open_next_period` → reprise mise à jour, pas de doublon.
6. **Gel** : passer 2026 `approved` → toute régénération de la reprise est refusée (immutabilité rétablie).

## 11. Risques / points ouverts

- L'exemption d'immutabilité doit être **strictement bornée** (un seul `source_type`, condition sur le statut de N) pour ne pas affaiblir l'invariant ailleurs.
- Le dédoublonnage `120` doit ré-aiguiller d'éventuelles écritures **postées** (immuables) → à faire via une migration contrôlée (potentiellement réaffectation `account_id` sur `ledger_entries`, à valider au moment du plan).
- Dépendance amont : la règle d'imputation des paiements à la période ouverte ([[payment_imputation_rules]] C) s'appuie sur l'existence du `450` reporté ; à brancher une fois l'à-nouveau en place.
