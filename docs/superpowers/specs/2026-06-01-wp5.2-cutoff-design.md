# WP5.2 Point 3 — Cut-off comptable générique (rattachement à l'exercice)

**Date** : 2026-06-01 · **Branche** : `v2` · **Statut** : design validé (2 audits adverses passés)

## 1. Contexte & objectif

La comptabilité de copropriété est une **comptabilité d'engagement / droits constatés** (décret n° 2005-240, art. 2 ; arrêté du 14/03/2005). Chaque charge et chaque produit doit être rattaché à l'exercice **qu'il concerne**, indépendamment de la date de facture ou de paiement. À la clôture, deux décalages doivent être corrigés (« cut-off ») :

- charges/produits **acquis en N mais non encore facturés/encaissés** → à constater dans N ;
- charges/produits **comptabilisés en N mais concernant N+1** → à reporter sur N+1.

Sans cut-off, le résultat de N et le bilan (annexe 1) sont **insincères**. Le grand livre étant la source légale, ces régularisations passent par des écritures.

Objectif : un **moteur générique de cut-off** (backend RPC) couvrant les 4 natures de rattachement, avec **extourne automatique** à l'ouverture de N+1.

## 2. Périmètre

**Inclus** : moteur backend (table + RPC SQL), 4 natures (CAP/CCA/PCA/PAR), extourne automatique, création à la volée des comptes de contrepartie, tests sur boucle d'or + copro jetable.

**Exclu** (différé) : UI de saisie ; lettrage / rapprochement FNP↔facture réelle (l'écart estimé/réel tombe en charge de N+1, ce qui est correct) ; gestion TVA (syndicat non assujetti, charges TTC) ; affectation/régularisation du résultat 120/110→450 (= WP5.3) ; séparation fine courant (120) / travaux (110), aujourd'hui tout le résultat 6/7 va en 120 (limite WP5.1).

## 3. Modèle de données — table `period_cutoff_items`

Source de vérité du rattachement d'un exercice N. Une ligne = un item de cut-off.

| Colonne | Type | Notes |
|---|---|---|
| `id` | uuid PK | `gen_random_uuid()` |
| `copro_id` | uuid NOT NULL | → `copros(id)` ON DELETE CASCADE |
| `period_id` | uuid NOT NULL | → `accounting_periods(id)` = exercice **N** |
| `kind` | text NOT NULL | CHECK `in ('CAP','CCA','PCA','PAR')` |
| `account_id` | uuid NOT NULL | → `accounts(id)`. Compte de résultat : 6xx/67x (charges) pour CAP/CCA ; 7xx (produits) pour PCA/PAR |
| `counterpart_account_id` | uuid NOT NULL | → `accounts(id)`. Compte de bilan de rattachement (cf. §4) |
| `amount` | numeric(15,2) NOT NULL | CHECK `amount > 0` |
| `label` | text NOT NULL | libellé métier (ex. « Entretien ascenseur déc. — facture à venir ») |
| `supplier_id` | uuid NULL | → `suppliers(id)`. Optionnel (CAP fournisseur) |
| `auto_reverse` | boolean NOT NULL | DEFAULT `true`. Extourné en N+1 ? `false` = dette certaine soldée par le paiement, jamais contre-passée (cf. §4) |
| `posting_tx_id` | uuid NULL | → `ledger_transactions(id)`. Écriture dans N |
| `reversal_tx_id` | uuid NULL | → `ledger_transactions(id)`. Extourne dans N+1 |
| `created_at` / `updated_at` | timestamptz | `now()` |

Les items **ne portent pas de `lot_id`** : le cut-off est collectif (rattachement global). Les comptes utilisés (408/486/487/461/421/431/432) ne sont pas des 45x, donc le trigger `enforce_lot_id_on_45x` ne s'applique pas (lot_id NULL accepté).

## 4. Les 4 natures et leurs écritures

Écriture **en N** (datée dans l'exercice N) ; **extourne en N+1** = inverse débit/crédit exact, datée du 1er jour de N+1.

| `kind` | Cas métier | Écriture en N | Contrepartie | Extourne N+1 |
|---|---|---|---|---|
| **CAP** — charge à payer | ascenseur entretenu déc. non facturé ; salaire gardien déc. ; charges sociales 4ᵉ trim. | `D account(6xx/67x) / C counterpart` | **408** (fournisseur) · **421** (salaire) · **431/432** (social) | `D counterpart / C account` |
| **CCA** — charge payée d'avance | assurance N+1 payée en N | `D counterpart(486) / C account(6xx/67x)` | **486** | `D account / C counterpart` |
| **PCA** — produit encaissé d'avance | loyer antenne-relais N+1 encaissé en N | `D account(7xx) / C counterpart(487)` | **487** | `D counterpart / C account` |
| **PAR** — produit à recevoir | loyer antenne facturé à cheval ; indemnité assurance acquise ; intérêts de placement courus (hors fonds ALUR) | `D counterpart(4618) / C account(7xx)` | **4618** (sous-cpte de 461) | `D account / C counterpart` |

**Décisions de compte tranchées (audits internes + recherche web)** :
- **PAR = 4618 « Produits à recevoir »** (sous-compte dédié de 461, actif/créance) — bonne pratique JPM-copro ; le `461` brut est jugé « vicieux », il reste un fallback documenté. **462 = erreur de sens** (compte de dettes), proscrit. Le compte produit (`account_id`) est choisi **par nature** : 716 (intérêts/produits financiers), 714 (loyer antenne, indemnités), 718 (exceptionnels).
- **Salaire à payer = 421**, charges sociales = **431/432** (jamais 408). Mais ce sont des **dettes certaines** → `auto_reverse = false` : soldées par le décaissement de janvier (D 421/431/432 / C 512), **pas** par contre-passation (sinon faux solde). Source : JPM-copro étude 7-6-8.
- **FNP / CCA / PCA / PAR estimés** = écritures d'inventaire (estimations) → `auto_reverse = true` : extourne au 01/01 N+1 ; la pièce réelle re-crée la charge/produit en N+1, l'extourne neutralise le double comptage.
- Conformité décret 2005-240 + arrêté 14/03/2005 **art. 10** confirmée par sources primaires (Légifrance) et professionnelles (ARC, JPM-copro, Compta-Online). Sens N + extourne vérifiés ; aucun double comptage (simulation 2 exercices).

## 5. Comptes de contrepartie — création à la volée

Il n'existe **pas** de table de plan comptable de référence ; les comptes vivent dans `accounts` par copro. `post_period_cutoff` fait un **upsert** des contreparties manquantes par code (contrainte `accounts_copro_code_unique (copro_id, code)` confirmée) :

```
INSERT INTO accounts (copro_id, code, name, account_type, is_system)
VALUES (..., :code, :name, :type, true)
ON CONFLICT (copro_id, code) DO NOTHING;
```

`name` est NOT NULL → libellés imposés (alignés sur `plan-comptable.ts`) :

| code | name | account_type |
|---|---|---|
| 408 | Fournisseurs - Factures non parvenues | liability |
| 421 | Personnel - Rémunérations dues | liability |
| 431 | Sécurité sociale | liability |
| 432 | Autres organismes sociaux | liability |
| 486 | Charges constatées d'avance | asset |
| 487 | Produits encaissés d'avance | liability |
| 4618 | Produits à recevoir | asset |

Le `4618` est créé comme sous-compte de `461` (`parent_id` = id du 461 s'il existe). Note : le seed historique nomme la FNP `410` ; on **standardise sur 408** (décret). Le `410` du seed sera borné séparément (hors scope strict de cette spec). Côté charges, le moteur est **agnostique** : `account_id` est un paramètre (l'app utilise `617` « Frais de personnel » là où le plan copro standard utiliserait 641/642 — divergence de plan sans impact sur le cut-off, à border séparément).

## 6. RPC `post_period_cutoff(p_copro_id, p_period_id, p_items jsonb)`

`SECURITY DEFINER SET search_path = 'public'`. Poste le cut-off de N.

1. **Garde** : période N doit être `open` (sinon erreur — cf. cycle §10). Refuser items `amount <= 0`.
2. Valider chaque item : `kind` valide ; classe de `account_id` cohérente avec `kind` (6/67 pour CAP/CCA, 7 pour PCA/PAR) ; `counterpart` cohérent (cf. §4).
3. **Upsert** des comptes de contrepartie manquants (§5), résoudre leurs `id`.
4. **Idempotent** : supprimer l'écriture cut-off existante de N (`source_type='closing' AND source_id=N AND period_id=N`) et les items de N, puis recréer. Le DELETE d'une écriture postée est autorisé par l'exemption d'immutabilité étendue (§9) tant que N n'est pas `approved`.
5. Insérer les items ; construire **une** écriture équilibrée (toutes natures regroupées) et la poster via `create_ledger_transaction(p_copro_id, N, date_clôture_N, '…', 'closing', N, entries, true)`.
6. Stocker `posting_tx_id` sur les items. Retour : `{success, items, total_par_nature, tx_id}`.

## 7. RPC `reverse_period_cutoff(p_copro_id, p_period_id)` — **interne**

`SECURITY DEFINER SET search_path = 'public'`. Poste l'extourne dans N+1. **Jamais point d'entrée public** : appelée uniquement par `open_next_period` (cf. §10, invariant « une seule période ouverte »).

1. Localiser N+1 (la période suivant N) ; elle doit être `open`.
2. **Garde gel** : si N **ou** N+1 est `approved` → refuser proprement (pas de régénération). Sinon, DELETE-recreate idempotent de l'extourne (`source_type='closing' AND source_id=N AND period_id=N+1`).
3. Pour chaque item de N **avec `auto_reverse = true`** : écriture inverse (cf. §4). Poster **une** écriture équilibrée via `create_ledger_transaction(p_copro_id, N+1, début_N+1, '…', 'closing', N, entries, true)`. Les items `auto_reverse = false` (dettes certaines : salaire, cotisations chiffrées) ne sont **jamais** extournés — ils sont reportés à-nouveau (comptes 421/431/432, classe 4) puis soldés par leur paiement en N+1.
4. Stocker `reversal_tx_id`. Retour `{success, …}`.

## 8. Modification de `open_next_period`

Après le post **réussi** du report à-nouveau (et avant le `RETURN` final), ajouter :

```
v_rev := reverse_period_cutoff(p_copro_id, p_closing_period_id);
IF NOT COALESCE((v_rev->>'success')::boolean, false) THEN
  RAISE EXCEPTION 'Extourne cut-off échouée : %', v_rev->>'error';  -- rollback report + extourne
END IF;
```

- **Ordre garanti** : report d'abord (dépose 408/486/487/461 en N+1) → extourne ensuite (les solde à 0).
- **Atomicité** : `RAISE` (pas `RETURN success:false`), car `create_ledger_transaction`/`post_ledger_transaction` avalent leurs erreurs ; sans RAISE, N+1 resterait avec un report sans extourne (à-nouveau faux).

## 9. Immutabilité — extension de l'exemption

Les 4 fonctions trigger (`trg_ledger_tx_immutable`, `trg_ledger_tx_no_delete_posted`, `trg_ledger_entry_immutable`, `trg_ledger_entry_no_insert_posted`, migration `20260601092000`) exemptent aujourd'hui **uniquement** `source_type='opening_balance'` tant que la période **source** n'est pas `approved`. Extension :

1. Couvrir `source_type IN ('opening_balance','closing')`.
2. **Double test** : exempter seulement si **la période source ET la période d'accueil** (celle du `period_id` de l'écriture) ne sont pas `approved`. Ferme le trou « modifier une écriture d'un exercice figé via une approbation dans le désordre » (ex. N approuvé / N+1 ouvert, ou inverse).
3. Factoriser le prédicat dans un helper (ex. `is_regen_exempt(source_type, source_id, period_id)`) pour ne pas le dupliquer 4×.

Effet : cut-off et extourne sont régénérables jusqu'à l'approbation, puis **figés**. Le flux WP5.1 normal (à-nouveau régénéré pendant que N+1 est ouvert) reste inchangé (double test trivialement satisfait).

## 10. Index d'unicité, cycle d'usage & invariants

**Index** : `CREATE UNIQUE INDEX ... ON ledger_transactions (copro_id, source_id, period_id) WHERE source_type='closing'`. Le `period_id` est **obligatoire** : cut-off (`period_id=N`) et extourne (`period_id=N+1`) partagent `source_id=N` ; sans lui ils collisionneraient. Ne pas calquer `uq_ledger_tx_opening_balance` (qui est sans `period_id`).

**Invariant « une seule période ouverte »** (`enforce_single_open_period`) : N et N+1 ne peuvent jamais être `open` simultanément. Conséquences :
- Cycle nominal : `reopen_period(N)` → `post_period_cutoff(N)` → `close_period(N)` → `open_next_period(N)` (reporte les 4xx **puis** extourne dans N+1).
- Corriger un cut-off **après** ouverture de N+1 : `reopen_period(N+1)` (referme N+1) → `reopen_period(N)` → `post_period_cutoff(N)` → `close_period(N)` → `open_next_period(N)` (régénère report + extourne ; `open_next_period` rouvre N+1 existant via son `UPDATE status='open'`).

## 11. Limites connues (documentées, non bloquantes)

- Résultat des travaux (67x) viré en **120** et non 110 tant que la séparation courant/travaux n'est pas faite (limite WP5.1). Mécaniquement sans danger.
- Pas de lettrage : l'écart entre FNP estimée et facture réelle s'impute en charge de N+1 (correct comptablement) ; un rapport de contrôle « FNP extournées vs factures reçues » est différé (P3).
- **Intérêts courus du fonds travaux ALUR** : exclus du PAR classique — capitalisés en **105** (réserve), pas en produit classe 7 (cf. mémoire ALUR). À traiter hors moteur ou via compte d'attente 471 ; ne pas router en 4618/716.
- **Dépréciations / provisions pour impayés** (491/492) : hors scope du moteur — elles ne s'extournent **jamais**.
- Collision théorique `unique_period_name (copro_id, name)` si une période homonyme existe avec d'autres dates — hors scope WP5.2.

## 12. Tests (sur copro jetable, puis boucle d'or 22222222)

1. **CAP fournisseur** (FNP 408) : posté en N → charge de N augmentée ; clôture + `open_next_period` → 408 reporté + extourne auto → 408 = 0 en N+1, charge nette N+1 = 0 après extourne ; vraie facture (D6/C401) en N+1 → charge comptée **une seule fois** (dans N).
2. **CAP social** (431/432) : contrepartie ≠ 408 correctement créditée.
3. **CCA** (486) : charge neutralisée en N, ramenée sur N+1.
4. **PCA** (487) : produit neutralisé en N, ramené sur N+1.
5. **PAR** (461) : produit constaté en N, créance soldée en N+1 à l'encaissement.
6. **Équilibre** : chaque écriture débit=crédit ; **Actif = Passif** post-cut-off ; 408/486/487/461 = 0 en N+1 après extourne.
7. **Idempotence** : rejouer `post_period_cutoff` puis `open_next_period` ne crée pas de doublon.
8. **Gel** : après approbation AG de N, cut-off et extourne figés (modification refusée).
9. **Dette certaine (`auto_reverse=false`)** : CAP salaire posté en N → **non extourné** en N+1 ; le 421 est reporté à-nouveau et se solde par le paiement (D 421 / C 512). Vérifier l'absence de contre-passation parasite.
