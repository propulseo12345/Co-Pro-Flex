# Glossaire technique CoProFlex (jargon de code / projet)

> Vocabulaire **technique propre au projet** (pas les concepts de programmation générale).
> Jumeau métier (copro + compta) : [/CONTEXT.md](../../CONTEXT.md). Un mot ne va que dans **un** des deux.
> Format : **terme** en gras + définition courte + `_Avoid_:` si un synonyme/anti-patron est à bannir.
> **Enrichissement au fil de l'eau** (y compris PR de rename/typo) : si tu croises ou renommes un terme technique ambigu, ajoute-le ici dans la même PR.

## Architecture & stack

- **coproflex-v2 (repo v2)** — le front v2 reconstruit from-scratch dans un **repo dédié** `coproflex-v2` (TanStack Start + **Tailwind CSS v4 + shadcn/ui**, bascule CSS Modules→Tailwind actée 2026-06-28). L'ancien front Next (`src/`) ET l'échafaudage `v2-tanstack/` (dossier dans ce repo) restent **gelés/abandonnés**, jamais modifiés. _Avoid_: « copier v1 » ; **CSS Modules** (ancienne stack) ; construire dans `v2-tanstack/` (échafaudage périmé, repo réel = `coproflex-v2`).
- **Server function / loader** — couche données du front : navigateur → server function (`createServerFn`, la « porte ») → **RPC SQL** → DB (décision D22). La double écriture comptable reste **dans une transaction SQL**, jamais sortie de la base. Amorcé dans `v2-tanstack/auth.ts`, pas encore déployé sur les features. _Avoid_: logique comptable côté client/edge.
- **Edge function** — réservée aux **cron/webhooks** uniquement (relances, alertes, banque GoCardless, statut emails), pas à la logique métier. Les ~26 edges v1 (0 déployée sur le live) meurent avec v1 et sont recréées proprement. `Implémentation:` patron pg_cron `0055`. _Avoid_: edge pour la logique métier ; réutiliser les edges v1.
- **Migration** — script SQL versionné `supabase/migrations/NNNN_*.sql` qui modifie la structure/les fonctions de la base. Appliquée par Claude sur le live (gouvernance tout-cloud). _Avoid_: « le repo migrations = source de vérité » (il a drifté — vérifier la base réelle).
- **CoProFlex live (qqfqrcolzmcbsvfaumiq)** — projet Supabase cloud de prod (compte perso), tout-cloud (Docker local abandonné, OOM Windows). Base quasi vide, RLS ON mais pas FORCE (à durcir), 0 edge déployée alors que le front en invoque 12+ (paiements/banque/AG cassés en prod). `Implémentation:` `.env.local` (`SUPABASE_PROJECT_REF`). _Avoid_: iyfesbjnkpynmwlsmxnp (ancien projet périmé) ; Supabase local pour ce chantier.
- **Multi-cabinet** — SaaS B2B multi-syndics : le cabinet est le tenant racine (`copros.cabinet_id` NOT NULL on delete restrict), RLS cloisonnée par cabinet. Rôles applicatifs = enum `membership_role` {gestionnaire, coproprietaire, platform_admin} ; anon/service_role sont des rôles Postgres, pas des valeurs d'enum. `Implémentation:` `create_copro` DEFINER (0083). _Avoid_: modèle mono-cabinet ; escalade gestionnaire→platform_admin via memberships (faille auditée).
- **Capacités dormantes** — capacités déjà au schéma mais non câblées en v1 (neutralisées par des valeurs en dur) : indivision d'un lot (`lot_owners.share_percent` / `is_primary`, 0010), versionnage temporel des clés (`repartition_keys.valid_from` / `valid_to`, 0009). La v2 les inventorie et les active. _Avoid_: reproduire la sous-exploitation v1 ; forcer `share_percent=100` / `is_primary=true` en dur.
- **HTML→PDF (stratégie PDF v2)** — cible v2 (décision AM1/TECH-1, **pas encore implémentée**) : actes (convocation, PV, état daté) en templates HTML rendus par un moteur headless (Chrome/Puppeteer) en server function, au lieu de jsPDF programmatique ; rend trivial un thème CSS par cabinet (white-label). NB : v1 et v2 embarquent encore jsPDF. _Avoid_: jsPDF programmatique pour le rendu riche.
- **Theming par tokens** — toute couleur/rayon/densité de l'UI est une **variable CSS** (token sémantique : `bg`, `surface`, `ink`, `accent`, `success`…) posée sur `<html>`, jamais une couleur en dur. Un changement de variable à la racine se propage à **toutes** les surfaces, y compris les éléments en *portail* (modals, calendriers, menus). `Implémentation:` `DESIGN_TOKENS.md` (Phase 3, à venir) + gate lint anti-`text-[#…]`. _Avoid_: couleur en dur dans le markup ; thème appliqué sur un sous-arbre (oublie les portails — bug v1).
- **Portail (portal) UI** — élément rendu **hors du flux normal du DOM**, tout en haut de la page (modal, menu déroulant, calendrier d'un sélecteur de date, tooltip). Piège v1 : un thème appliqué à un sous-arbre ne l'atteignait pas → calendrier resté clair en mode sombre. Résolu en v2 par les tokens à la racine + primitives **shadcn/Radix possédées**. _Avoid_: styler un portail avec des couleurs en dur.
- **Mode sombre** — 2ᵉ jeu de valeurs des tokens (surcharge `html.dark` du `:root` clair). Indy sombre = **brun-anthracite chaud** (pas un gris ardoise froid). Conçu **token-first dès le départ** (coût borné au fichier de tokens), jamais rajouté après coup. `Implémentation:` preuve `coproflex-v2/.planning/da-concours/da1-indy/proof-theme.html` ; `DESIGN_TOKENS.md` (Phase 3). _Avoid_: ajouter le sombre après coup (oublie des surfaces — piège v1).
- **White-label / personnalisation cabinet** — surcharge de marque **bornée**, par cabinet/tenant, stockée en base et injectée en variables à la racine : **logo + couleur d'accent + défaut clair/sombre + préréglage densité**. **Verrouillés** : couleurs sémantiques, structure, polices. 3 calques : socle Indy immuable → marque cabinet → thème clair/sombre. `Implémentation:` FRONT-8 ; `DESIGN_TOKENS.md` (Phase 3). _Avoid_: laisser un cabinet changer polices/sémantique/structure (casse a11y + cohérence).
- **Routes minces / features grasses** — règle d'organisation v2 : `src/routes/` ne porte que l'URL (path + garde d'auth + montage d'un composant), zéro métier ; tout le métier vit dans `src/features/<catégorie>/{components,hooks,api,functions,schemas}`. `src/shared/` = châssis transverse. `Implémentation:` `coproflex-v2/docs/ORGANISATION.md` (FRONT-9). _Avoid_: requête/calcul métier dans une route ; server function inline dans une route.
- **Frontière outillée (API publique par feature)** — chaque feature expose un `index.ts` maigre = son contrat ; on n'importe une AUTRE feature que via cet index, jamais ses fichiers internes. **Rendu obligatoire par le lint** (`eslint-plugin-boundaries` v5 : `element-types` + `entry-point` en error) — sans le lint, un LLM contourne. Pas de barrel racine (`sideEffects:false`). `Implémentation:` ORGANISATION.md §4 (FRONT-9). _Avoid_: convention de frontière en prose seule ; barrel racine agrégeant les features.
- **Specimen canonique** — pour chaque type d'artefact (route mince, server function→RPC, table dense, formulaire Zod+RHF, write de domaine), UN fichier « gold » validé à la main, nommé dans `CLAUDE.md`, que l'IA copie. Antidote n°1 au « copier le v1 gelé » (l'IA imite l'exemple le plus proche, pas la règle écrite). `Implémentation:` pilote finance (FRONT-3) = 1er specimen. _Avoid_: laisser l'IA s'inspirer de `../Co-Pro-Flex/src` (v1 gelé).
- **Workflow OS (statuts)** — chaîne canonique d'un ordre de service (enum `service_order_status`) : draft → sent → awaiting_provider → scheduled → in_progress → completed → closed (+ refused, cancelled). Transitions verrouillées par `is_valid_service_order_transition`. `Implémentation:` enum 0003 ; matrice 0032. _Avoid_: libellés FR figés en dur (« BROUILLON », « ENVOYE »…) au lieu de l'enum SQL ; oublier la réouverture completed→in_progress.
- **generate_document_path (chemin GED)** — fonction canonique 4 args `(uuid, document_category, integer, text)` qui calcule le chemin de stockage `ged/<copro>/<category>/<year>/<file>`, STABLE, G-INTERNAL (REVOKE anon). `Implémentation:` 0031. _Avoid_: la surcharge legacy à 3 arguments (jamais recréée dans le schéma canonique).
- **Tracking d'envoi AG** — table canonique de suivi des envois de convocations/PV (statut, méthode, tracking_ref, doc lié, horodatages). `Implémentation:` `ag_envoi_tracking` (0017). _Avoid_: `ag_notifications` / `ag_notification_events` / hook `useAgNotifications` (îlots transitoires quasi vides — mais cf. « Câble derrière le meuble »).

## Grand livre — mécanique

- **RPC canonique** — la **route d'écriture unique** d'une opération. Toute écriture au GL passe par `create_ledger_transaction` (0025), qui porte le verrou de période (`status='open'`, raise 23514 sinon). _Avoid_: dupliquer la garde dans chaque writer ; un 2ᵉ chemin d'écriture pour une même opération (« un chemin par feature ») ; INSERT brut dans `ledger_transactions`/`ledger_entries`.
- **source_type** — étiquette de l'écriture (`call_for_funds`, `payment`, `opening_balance`, `result_allocation`, `works_settlement`, `closing`…) ; sert au filtrage des audits et des annexes.
- **operation_id** — dimension **non-GL** portée au **niveau de la ligne** (`ledger_entries.operation_id`, FK budgets ON DELETE RESTRICT) pour rattacher une charge à une opération travaux. **Précédence stricte** : ligne non-NULL ⇒ classée TRAVAUX quoi que dise `accounts.charge_nature` (ex. subvention 711 basculée en travaux). Re-étiquetable sans toucher aux montants. `Implémentation:` 0060 ; lue par `create_ledger_transaction`, `open_next_period`, `v_result_allocation_split`, `settle_works_balance`. _Avoid_: la confondre avec la garde multi-clés `repartition_key_id` (portée en EN-TÊTE par `call_for_funds_lines`, B5/0058).
- **charge_nature** — classification **binaire** d'un compte de classe 6/7 : `courant` / `travaux`, lue par `open_next_period` et `v_result_allocation_split` au lieu d'une liste de codes en dur. Sourcée arrêté 14/03/2005 (6221=travaux, 711=courant par défaut, 662=agios courant). `Implémentation:` `accounts.charge_nature` + CHECK `ck_accounts_charge_nature` (0059) ; RPC `set_account_charge_nature` (0068) ; correctifs 0067/0069 (662→courant). Les comptes « contextuels » basculent par `operation_id`, pas par compte. _Avoid_: liste de codes en dur ; 662 classé travaux (corrigé 0069).
- **CHECK miroir charge_nature** — `ck_accounts_charge_nature` : `charge_nature` obligatoire ssi compte de classe 6 ou 7, interdite ailleurs. Le CASE est explicite (`is not null`) car un CHECK passe quand l'expression vaut NULL. `Implémentation:` 0059. _Avoid_: écrire seulement `charge_nature in (...)` (laisse passer un 6/7 à NULL).
- **Doctrine des états (G24-T11)** — deux familles : (1) statut **conséquence des comptes** (payé/soldé/réalisé) = **TOUJOURS calculé depuis le GL via une vue**, jamais un drapeau stocké ; (2) statut **événement/décision** (AG, OS, recouvrement) = **stocké** mais changé **uniquement par une fonction de transition serveur unique et gardée**, jamais par un UPDATE éparpillé.
- **Grand livre = source unique** — tout solde/indicateur dérive des écritures du GL, jamais d'un compteur parallèle. Les divergences (créances lues sur `call_for_funds_lines`, réalisé lu sur `budget_expenses`) sont des bugs à réunifier. `Implémentation:` `ledger_entries`/`ledger_transactions` (0013) ; `audit_finance_integrity` (0028). _Avoid_: double source de vérité.
- **Immutabilité du GL** — une écriture postée n'est ni supprimée ni repassée en draft (4 triggers en-tête + lignes, 0024). On corrige par contre-passation (`reverse_ledger_transaction`, 0071) ; un GL pollué ne se nettoie pas, on bascule sur une copro neuve (11111111 abandonnée pour 22222222). _Avoid_: DELETE d'une écriture postée ; retour posted→draft.
- **Exemption immutabilité (is_ledger_regen_exempt)** — liste blanche autorisant l'annule-et-repasse UNIQUEMENT pour 4 source_types régénérables (`opening_balance`, `closing`, `opening_onboarding`, `result_allocation`) ET tant que ni la période source ni la période d'accueil ne sont `approved`. `Implémentation:` 0024. _Avoid_: réécrire un à-nouveau d'un exercice approuvé ; croire que l'exemption couvre paiements/appels/factures.
- **Porte « Annuler » (contre-passation)** — une seule porte routant par nature vers 4 fonctions métier (`reverse_payment` 0087 / `cancel_call_for_funds` 0071 / `cancel_supplier_invoice` 0087 / `reverse_period_cutoff` 0027), socle commun = `reverse_ledger_transaction`. Règle « stylo, jamais gommer » : on écrit la ligne inverse. _Avoid_: exposer `reverse_ledger_transaction` ou `unallocate_payment` à l'UI (INTERNE/service_role only) ; annuler sur un exercice approuvé.
- **Trigger contrainte différé à image figée** — piège PG : un CONSTRAINT TRIGGER DEFERRABLE rejoue au COMMIT avec l'image figée de la ligne, pas un re-fetch. Correctif : re-lire l'état courant via la PK (`new.id`) dans le corps. `Implémentation:` `tr_cff_ledger_required` (0026, resserré 0071). _Avoid_: lire `new.status`/`new.ledger_tx_id` figés au lieu de re-quêter la ligne par sa PK.
- **Arrondi cumulatif déterministe** — allocation du centime résiduel par télescopage du plus-grand-reste : `part = round(cible × cumul/Σ) − round(cible × (cumul−poids)/Σ)`, `cumul = sum(weight) OVER (PARTITION BY key ORDER BY lot_id ROWS UNBOUNDED PRECEDING)`. Garantit Σ lots = cible exacte par clé, ordre stable. `Implémentation:` `post_budget_call_for_funds` (0026). _Avoid_: tolérance ±1 cent ; appel annuel unique pour contourner le centime.
- **post_budget_call_for_funds (appel canonique)** — RPC unique **10 args** créant un appel en partie double : D 450-x par lot (agrégé toutes clés, plus-fort-reste) / C 701 (courant) · 702 (travaux) · 105 (réserve ALUR). `Implémentation:` 0026. _Avoid_: `post_call_for_funds` (mono-clé, banni, n'existe pas) ; la surcharge **8 args** (legacy wp6, perd des centimes) ; INSERT direct `call_for_funds`.
- **post_supplier_payment idempotent** — règlement fournisseur (D 401 / C 512) protégé du double paiement par clé d'idempotence : signature canonique **8 args** (8e = clé). `Implémentation:` 0026 (cr5). _Avoid_: la surcharge **7 args** (non idempotente, double paiement possible).
- **INSERT direct sans écriture comptable** — anti-patron : créer un fait financier (appel, charge, dépense) par INSERT sans passer par le GL. En partie double tout fait financier doit générer une écriture équilibrée via `create_ledger_transaction`. _Avoid_: `generate_combined_calls_from_ag` (abandonnée : INSERT `call_for_funds` sans posting) ; tout chemin hors `create_ledger_transaction`.
- **is_postable / is_system (chapeau 450)** — au seed, le compte 450 est le seul chapeau agrégateur : `is_system=true` (protégé), `is_postable=false` ; tous les sous-comptes 450-x sont postables et portent `nature` (`ck_nature_only_on_45x`). `Implémentation:` `provision_copro_chart` (0025). _Avoid_: poster directement sur le chapeau 450 ; rendre un 450-x non postable.
- **provision_copro_chart** — `provision_copro_chart(uuid)` sème le plan de comptes copro (classes 1/4/5/6/7) avec `charge_nature` ; source unique de la classification, appelée par `create_copro` (0083). `Implémentation:` 0025 (redéf. 0056/0059/0067/0069). _Avoid_: réécrire un plan de comptes parallèle ; lister les comptes ailleurs.
- **open_next_period** — ouvre l'exercice N+1 : reporte les à-nouveaux de bilan (1xx/4xx/5xx par compte×lot), déverse le résultat **courant→478** et **travaux→12**, contre-passe le cut-off de N. Idempotente par remplacement tant que ni N ni N+1 ne sont approuvés ; exige N clôturée. `Implémentation:` 0027, version vivante 0060 (split par `charge_nature` + `operation_id`). _Avoid_: rejouer sur un exercice approuvé ; confondre les comptes d'attente avec 110/120 (renommés 12/478 en 0056).
- **v_result_allocation_split** — vue garde-fou anti faux-vert de l'affectation du résultat (1 ligne = incohérence). Contrôle systématiquement la branche courante (478/450-1), la branche travaux (12/450-2) seulement si déversée. Assiette de `assert_result_allocation_split` (rollback en fin de `regularize_period`). `Implémentation:` 0027, vivante 0060. _Avoid_: se fier au nom des colonnes (`mv_120`=compte 478 COURANT, `mv_110`=compte 12 TRAVAUX — non renommables via CREATE OR REPLACE VIEW) ; se fier à `result_net` (hors logique depuis 0060).
- **Convention crédit-débit (affectation)** — dans `v_result_allocation_split`, les mouvements d'affectation sont calculés en **crédit-débit**, à l'OPPOSÉ de `open_next_period` (débit-crédit) : voulu et commenté (« NE PAS aligner »), car l'écriture déverse 12x→45x. `Implémentation:` CTE `result_src`, 0060. _Avoid_: aligner les deux conventions (casse le garde-fou).
- **Atomicité de l'activation AG (tout-ou-rien)** — `activate_ag_decisions` (0030) parcourt `ag_pending_actions` 'pending' dans un ORDRE imposé (budgets → appels → APPROVE_ACCOUNTS en dernier), dans **une seule transaction** : toute erreur = rollback global (pas de savepoint par action). Idempotence = les actions 'activated' sont sautées. _Avoid_: prétendre à un savepoint/reprise partielle (inexistant) ; croire qu'une action échouée n'annule pas les autres.
- **action_type (auto-population AG)** — étiquette (`ag_action_type`) sur une résolution qui déclenche la matérialisation d'une `ag_pending_actions` puis la création de l'objet métier. Sans `action_type` la résolution est « muette ». Bug v1 : `createStandardResolutions` (front) laisse `action_type=NULL` (RUPTURE 1) alors que la RPC `create_ag_with_standard_resolutions` le pose. _Avoid_: créer des résolutions standard sans `action_type` ; exposer le code brut côté UI.
- **start_ag / close_ag / prepare_ag_decisions / activate_ag_decisions / finalize_ag / archive_ag** — chaîne RPC de cycle de vie AG (definer, garde gestionnaire/service). Ordre impératif : **`close_ag` (fige+approuve les votes via `calculate_resolution_result`) PUIS `prepare_ag_decisions`** (matérialise les seules 'approved' en file 'pending') ; activation **une seule fois à l'étape PV** ; `finalize_ag` ouvert dès `pv_signed`, ne relance jamais l'activation. `Implémentation:` 0030 ; `finalize_ag` 0040. _Avoid_: inverser close/prepare (0 décision, échec silencieux) ; activation manuelle bloc par bloc.
- **calculate_resolution_result** — sous-fonction appelée en boucle par `close_ag` : calcule le résultat de chaque résolution selon sa majorité (art24/25/25-1/26/26-1/unanimité + passerelles) et fige son statut 'approved'/'rejected' (une résolution sans vote → 'rejected', choix assumé). `Implémentation:` 0030. _Avoid_: recalculer les votes hors de cette fonction.
- **generate_calls_from_ag_payload** — fonction canonique (0030) qui, pour une résolution d'échéancier, résout le budget 'validated' sur période 'open', lit le mode (UNIQUE/SEMESTRIEL/TRIMESTRIEL/PERSONNALISE) et boucle sur `post_budget_call_for_funds` (qui fait la ventilation multi-clés). _Avoid_: `generate_combined_calls_from_ag` (abandonnée : front, mono-clé, INSERT directs) ; lui attribuer la ventilation.
- **Budget né à l'activation** — CIBLE v2 (D29, **pas implémentée**) : faire naître le budget réel à l'activation AG, atomiquement, en écrivant `budgets.source_ag_id` (colonne existante 0016). Aujourd'hui le budget est créé en amont (front/onboarding) et `activate_ag_decisions` ne fait que le `validate_budget`. _Avoid_: présenter `create_budget_from_ag_resolution` comme existant (n'existe pas) ; budget fantôme sans lien `source_ag_id`.
- **in_progress (repli AG)** — valeur de l'enum `ag_status` servant de repli en cas d'annulation de séance (la séance ouverte normale est `session_active`). Les statuts `pv_*` sont posés par UPDATE front, pas par une fonction serveur. `Implémentation:` enum 0003. _Avoid_: confondre avec `session_active` ; le poser via une fonction de transition serveur.

## Tests & vérification

- **Gate** — test SQL d'invariant (`supabase/tests/gate_*.sql`) qui PROUVE une propriété en **valeur** (pas seulement IS NOT NULL), tests négatifs (le forbidden doit lever), croisé avec la source canonique, sur copro seedée. Doit être **vert** avant merge. Le runner sépare GATES (bloquantes) et DEFERRED_GATES. `Implémentation:` `scripts/db-test.mjs` (`npm run db:test`, claim service_role en tête). _Avoid_: « skipper »/truquer un gate ; assertions IS NOT NULL au lieu de valeurs ; fallback auto-réparant (faux vert).
- **Golden / boucle d'or** — copropriété de référence (`22222222` « Le Clos Saint-Michel », exercice ouvert) aux valeurs vérifiées, qui reste **inchangée** (parité du résultat comptable, pas le nombre d'anomalies historiques) après toute migration finance. `Implémentation:` `seed_golden_loop` (0029) ; `tests/…_socle_acceptance_test.sql`. _Avoid_: modifier la boucle d'or (immuable) ; `11111111` comme copro active (témoin abandonné, GL pollué ineffaçable).
- **Harnais** — fonctions qui fabriquent une copro **jetable** taguée HARNESS, pour tester en isolation sans toucher la boucle d'or. `create_test_copro` bâtit une structure synthétique propre (≠ clone) + 1 exercice ouvert ; `create_test_copro_seeded` y déroule `seed_golden_loop` (0 écart à l'audit = invariant). `Implémentation:` 0029 ; alias documentés `create_clean_test_copro(_seeded)`. _Avoid_: décrire le harnais comme un clone par TEMP TABLE (ancien legacy) ; traiter les alias comme des doublons.
- **Test en BEGIN/ROLLBACK** — pattern de test SQL annulé en fin (rien persisté), précédé du claim service_role (pour passer `is_service_call`). Prouve une migration sur le cloud vierge sans le polluer ; revers : masque les contraintes DEFERRED (vérifiées au COMMIT seulement). `Implémentation:` `set_config('request.jwt.claims', …)` ; API Management `/database/query`. _Avoid_: tester une contrainte DEFERRED en begin/rollback (promouvoir le gate à commit réel) ; oublier le claim service_role.
- **audit_finance_integrity** — fonction qui doit renvoyer **0 écart** ; condition de la DoD finance. Porte notamment le check LOT_GL_MISMATCH (0028).
- **v_lot_vs_gl_mismatch** — vue d'audit (security_invoker) comparant par lot le solde GL des 45x — **restreint aux source_type `call_for_funds` + `payment`** (colonne `gl_call_payment_balance`) — au relevé d'appel (`call_for_funds_lines`, dû−payé). Le filtre évite un faux écart multi-période. `Implémentation:` 0028, recréée 0071. _Avoid_: comparer tout le solde 45x sans filtre (faux LOT_GL_MISMATCH) ; supposer une colonne `gl_balance`.
- **Gate de cohérence croisée (annexes)** — famille de contrôles d'invariant ENTRE annexes (annexe 1 équilibrée, 12 = col. E annexe 5, annexe 2 = 3/4, avance 1031 ≤ 1/6 budget, 47 non soldés signalés), **en partie à coder** : seul `gate_0075_annexes_coherence.sql` existe (couverture partielle). _Avoid_: vérifier une annexe isolément ; présenter ces contrôles comme tous en place (la plupart au stade spec).
- **DoD** — Definition of Done stricte par feature (tsc 0 · unit · **e2e Playwright qui PROUVE en base** : count/somme exacts, jamais un 200/redirection · non-régression · lint · /simplify · code review multi-agents · vérif navigateur · PR+push ; + base : revue cascade + BEGIN/ROLLBACK + Advisor 0 ; + finance : `audit_finance_integrity`=0 + équilibre GL + golden inchangé). `Implémentation:` skill `methodo-coproflex`, note `rules-v2.md`.
- **Revue d'impact en cascade** — grosse revue d'impact obligatoire AVANT chaque migration : migration simple = sous-agent ciblé, à enjeu = revue adversariale multi-agents, suivie d'un test BEGIN/ROLLBACK avant apply. _Avoid_: appliquer une migration sans revue cascade ni BEGIN/ROLLBACK.
- **Boucle d'auto-réparation Playwright** — cycle de construction autonome : TDD → réparer jusqu'au vert RÉEL (jamais skip/désactiver/truquer un test ; LIMITE de tentatives par point puis on passe ; « attendu ambigu/comptable » = STOP + question) → /simplify + re-test → code review multi-agents → PR. _Avoid_: truquer un test pour sortir de la boucle ; brûler la nuit sur un seul test.
- **Test e2e de parité** — « feature finie » = un clic réel Playwright sur l'écran v2 qui PROUVE l'effet EN BASE (`audit_finance_integrity`=0), jamais un 200/redirection. La parité porte sur le RÉSULTAT comptable, pas la reproduction des défauts v1. _Avoid_: parité par recopie des défauts v1.
- **CI anti-faux-vert (B9)** — pipeline CI v2 décidé : Linux strict `npm ci` → tsc → build → health-check HTTP (until-200) → e2e → vitest → gates, exigeant une PREUVE EN BASE (service-role), suite e2e jouée contre Next ET Start (golden de parité). C'est la cible : le `ci.yml` actuel reste v1 (tsc + lint + vitest + db:test). _Avoid_: valider sur un 200/redirection ; piège Windows exit-0.
- **Horloge métier injectable** — source de date métier injectée (concept `asOf`) branchée sur la période ouverte, pour toute date métier (tx_date, due_date, exercice) ; garantit justesse (jours francs, cut-off) et golden déterministe. Décision v2 E8 en PRINCIPE, mécanique non encore spécifiée. _Avoid_: `new Date()` / `Date.now()` pour une date métier ; figer `created_at` comme date métier.
- **Seed-to-golden** — stratégie de seed v2 : construire d'abord la golden « E2E-GOLDEN Domaine des Tilleuls » par le vrai chemin UI, puis CAPTURER le seed depuis cette copro, plutôt qu'une fixture écrite à la main (garde-fou anti-dérive seedée ≈ construite). `Implémentation:` `create_test_copro_seeded` ; `seed_golden_loop`. _Avoid_: copro-jouet (base 1 000 / 7 lots, abandonnée) ; fixture écrite à la main qui diverge de l'UI.

## Gardes & autorisation

- **G-MGR / G-SVC / G-DEF-RO** — annotations de garde sur les fonctions SQL : gestionnaire requis / appel service (`is_service_call()`) / definer read-only. Vérifier `is_service_call()` dans les gardes.
- **is_service_call() (garde DEFINER)** — les fonctions sensibles DEFINER (`provision_copro_chart`, `open_next_period`, posteurs GL…) exigent soit `is_service_call()`, soit `user_is_copro_manager()`, sinon RAISE `42501` « forbidden ». Cette garde **dans le corps** est le seul rempart (DEFINER bypasse la RLS). EXECUTE retiré de public/anon. `Implémentation:` helpers 0023, gardes répétées 0025/0026/0027. _Avoid_: exposer ces RPC à anon/public ; compter sur la RLS pour protéger un corps DEFINER.
- **Fuite SECURITY DEFINER (IDOR cross-tenant)** — une RPC DEFINER exposée à `authenticated` sans garde interne laisse un gestionnaire atteindre un autre cabinet. Règle : ouvrir le corps par `is_service_call()` OU `user_is_copro_manager()`/`user_has_copro_access()` sur le `copro_id` dérivé, sinon lever 42501. `Implémentation:` gate `gate_rls_definer_guards.sql` ; pattern généralisé 0025+ (corrigé 0045). _Avoid_: grant authenticated sur DEFINER sans garde interne.

- **Récursion RLS inter-tables** — piège : un `EXISTS(autre_table)` dans une policy est soumis à la RLS de la table jointe ; deux tables qui s'interrogent → récursion infinie (42P17) en prod, invisible en dev RLS off. ## Conventions de chantier

- **Préfixe de chantier** — un chantier = un **préfixe unique** pour numéroter ses décisions (ex. `G24-*` cadrage PARTIE C, `UX-*`, `GLOSS-`). Jamais réutiliser une lettre/numéro d'un autre chantier. _Avoid_: « C2 » ambigu entre deux chantiers.
- **rules-v2.md** — note des RÈGLES v2 **réinjectée à chaque message** (hook `UserPromptSubmit`). Décision de **méthode** → mettre à jour le skill `methodo-coproflex` + `rules-v2.md` ; décision **produit** → `REFONTE_DECISIONS`.
- **CHANTIERS.md** — registre des chantiers (statuts) pour ne pas oublier un travail commencé. `Implémentation:` `.planning/CHANTIERS.md`.
- **Mapper snake↔camel** — obligatoire entre la base (snake_case) et le front (camelCase) ; ne jamais consommer le brut.
- **Conventions de nommage SQL (pk_/uq_/idx_/ck_)** — Phase 0 : PK nommées `pk_<table>`, CHECK `ck_` (jamais `chk_`), unicité `uq_`, index `idx_` ; fichiers de migration purement numériques (le CLI rejette un suffixe alpha type `0013b`, d'où `0013b→0014`). _Avoid_: PK inline anonymes ; préfixe `chk_` ; suffixe alpha.
- **Piège placeholder %% en plpgsql** — le SQL inline des docs/plans affiche un double `%` (échappement markdown), or un placeholder plpgsql = un seul `%` (nb `%` = nb d'args). À garder en `%` simple, sinon `RAISE`/`format()` plante (latent : un db reset peut passer si le chemin n'est pas exercé). _Avoid_: laisser `%%` dans un `raise`/`format()`.
- **Piège ALTER TYPE ADD VALUE (55P04)** — le CLI enveloppe chaque migration dans une transaction ; `ADD VALUE` y est permis (PG12+) MAIS lève 55P04 si la valeur est UTILISÉE dans la même transaction (prédicat d'index, `=`). Contournement : prédicat en négatif (`status not in (...)`) ou isoler l'`ADD VALUE`. Une valeur seulement citée dans un CORPS de fonction est sûre. `Implémentation:` 0079. _Avoid_: référencer la nouvelle valeur d'enum (index/`=`) dans la migration de son `ADD VALUE`.
- **Base v2 = squash + clean** — baseline 0001 prévue pour le futur projet Supabase v2 = squash + nettoyage du schéma live (0087) : préserver la correctness (RPC/RLS/fixes prouvés), jeter l'archéologie/doublons/orphelins. Arbitrée (E13-q), **pas exécutée** (v2-tanstack n'a aucune migration). _Avoid_: recréer `post_call_for_funds` (banni) ; reprendre les outils de test internes (`force_delete_test_copro`) ; reprendre l'orphelin/non-canonique.
